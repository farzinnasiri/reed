# UI v2 migration: plan and checklist

> **Archived 2026-10-07.** The UI v2 migration is finished. This checklist is historical. `DESIGN.md` and `prototypes/redesign/home.html` are the UI sources. Planned sessions and session actions have since shipped. `DESIGN.v2.md` was renamed to `DESIGN.md`. Links below assumed this file still lived in `docs/plans/`.

- **Started:** 2026-10-01
- **Product owner:** Farzin
- **Goal:** Move the Expo app to the v2 "Companion" UI: one home screen (Pulse, thread, dock), Reed as a living presence, warm dark surfaces, no glass. Keep business rules and the workout logging UX as they are.
- **Sources of truth:**
  1. `DESIGN.v2.md`: tokens, rules, component contracts.
  2. `prototypes/redesign/home.html`: the interactive mockup (open it in a browser; frame 01 is live; tap the Pulse, "F" and the steppers).
  3. This file: order of work, scope, decisions, contracts.

  If these disagree, `DESIGN.v2.md` wins over the mockup. Record the disagreement in the handoff log at the bottom instead of guessing.

## 1. Scope

### In scope
- The Expo app (`app/`, `components/`, `design/`, `lib/` UI helpers) on Android, iOS and Expo web.
- New home: Pulse, thread modes (today/chat), presence corner, dock, "You" sheet.
- Reskinning every other surface with v2 tokens: workout module, sheets, onboarding, auth entry.
- The backend additions listed in the backend track (all additive).

### Out of scope
- New domains: Planned Sessions, routines, Reed writing to live sessions. They appear in the mockup, but they are later bets (Phase 8) that need their own PRD and approval.
- Any change to training math, insight generation, notification logic, or the coaching agents' behaviour, beyond the contracts below.

### Approved changes (these are not surprises)
- Dark only. The light theme and the appearance setting are removed.
- Glassmorphism, blur and backdrop diffusion are removed.
- Outfit becomes Figtree; v1's 800/900 weights and uppercase tracked labels go.
- Reed's header becomes the **Pulse** plus the "You" button.
- The action row (Start session / Quick log / Progress) becomes the **dock** (session button + composer). Quick log moves into the composer's `+` menu.
- The Progress page becomes the **expanded Pulse**. The You page and the Settings page merge into the **"You" sheet**.
- Reed's replies lose the avatar; the mascot moves to the hero (today mode) and the presence corner (chat mode).
- Today mode on open, then chat mode with infinite scroll-up history.
- Proactive "today cards" (weigh-in, quick log) and typed widgets in chat (generative UI v1).

### Must not change: the "no surprises" list
If a task seems to require changing any of these, stop and ask Farzin.

- **Session logging UX:** the Sessions page (start/resume, history, ongoing session row), the timeline page, the capture view, the swipe card (swipe right to log or save), metric pickers, warm-up/details/fail modifiers, unilateral left/right, the rest view and rest ring, live cardio, the add-exercise sheet (search, favorites, bulk add), session notes, the ended-session status strip and insights sheet. **Reskin only.**
- **Start/resume semantics:** starting opens an empty draft (`intent: start`); an open session always resumes; empty sessions are never persisted (AGENTS.md invariant 9).
- **Quick log:** presets, groups (strength/cardio/recovery), input kinds and the logging flow.
- **Every Progress stat:** the From Reed note, Training (Week/30D/90D, sets/reps/load, muscle split, top exercises), Consistency, Bodyweight (trend + log weight), Goals (+ full goals list, create/complete/archive).
- **Profile and settings capabilities:** body status, goals, training setup and the Training Profile editors (onboarding steps reused for editing), coach-update notifications, sign out, delete account with confirmation.
- **Chat capabilities:** typed and voice input, image attachments and the image editor, copy message, retry failed reply, starter quick actions, check-ins and post-session coach notes, related-session links, pagination, the scroll-to-latest affordance.
- **Deep links:** push notifications route by `data.screen` (`lib/push-notifications.ts`): `reed`, `home`, `goals`, `you`/`profile`, `progress`, `workout`. All must keep landing in the right place.
- **Onboarding flow, auth flow, notifications, analytics events** (`lib/analytics.ts`): keep the events; add new ones for new UI where useful.

Each one has a reason and a "reconsider if". Agents should not re-open these without a concrete problem.

### 2.1 Libraries

### 2.2 Animations
Fully specified in `DESIGN.v2.md` → Motion. Implementation notes:
- Add `reedSprings.morph = { duration: 550, dampingRatio: 0.92 }` and `reedSprings.sheet = { duration: 450, dampingRatio: 1 }` to `design/motion.ts`. Use Reanimated's `withSpring` with these configs. Pass `reduceMotion: ReduceMotion.System` and provide the crossfade fallbacks described in the design doc.
- **Mascot glide:** one `ReedMascot` instance in an absolutely positioned overlay inside the home surface. The hero slot and the corner slot are invisible placeholders that report their rects (`onLayout` → shared values). The overlay animates `translateX`, `translateY` and `scale` between them. Do not use shared-element transitions (they are for screen changes) and do not render two mascots.
- **Pulse:** one `Animated.View` driven by a single `progress` shared value (0 = strip, 1 = expanded). Derive `top/left/right/height/borderRadius/backgroundColor` and the content opacities from it with `interpolate`. Tap runs `withSpring(1, morph)`. A Gesture Handler `Pan` on the strip writes `progress` from the finger and snaps on release. The stage recede and the scrim derive from the same value.
- **Do not add** `LayoutAnimation` calls, Reanimated `entering`/`exiting` layout animations inside lists (they break web; see `use-entry-animation.ts`), or per-screen springs.

### 2.3 Generative UI = a typed widget catalog
- Reed **picks** a widget kind and supplies **references** (ids, preset keys). It never produces layout or styling.
- The catalog lives in one backend module (`convex/reedWidgets.ts`) as Convex validators. Client types come from the generated API types. The client registry (`components/reed/widgets/registry.tsx`) maps `kind → component`; unknown kinds render nothing.
- Widgets render **live data** through existing queries. Stored widget payloads hold references, never copied numbers.
- v1 kinds: `session_summary`, `weigh_in`, `quick_log`. Later: `plan`, `session_change`.
- The LLM emits widgets only through a structured-output/tool schema (zod) that the backend validates before storing. Invalid output means a text-only reply, never an error shown to the user.

### 2.4 Today vs chat on open
- **Today mode** if there is an unseen coach note (`isCoachNote` assistant message newer than the locally stored "last seen" marker), or if `reed.getPresence().reentryState === 'cold'` (last message more than 60 minutes ago).
- **Chat mode** otherwise: `hot`/`warm` with nothing unseen. Resume at the bottom of the thread.
- The "last seen" marker is client-side for now (SecureStore/localStorage, same pattern as `use-coach-message-unread.ts`). Promote it to the backend only if multi-device confusion shows up.
- Today content when there is no coach note: a deterministic greeting (time of day + one line about the week from the Pulse data) and the existing `reed.listQuickActions` starters as chips. No LLM call on open.

### 2.5 Today cards are derived, not stored
Cards like weigh-in and quick log are computed by a backend query from facts (`home.getTodayCards`). A card disappears when its condition stops being true (you weighed in today). Dismissal is client-side for the local day. Nothing new is persisted for them.

### 2.6 Theme strategy: retoken first, then rebuild
Phase 0 maps the **existing** `ReedTheme` colour keys to v2 values (for example `glassFill → surface`, `controlFill → surface`, `inputFill → surface`, `accentPrimary → accent`). It forces dark mode and turns blur off. That reskins the whole app at once, including the workout module, with no layout changes. New v2 components then use new token names. v1 keys are deleted in cleanup.

## 4. How the work is split

There are two tracks that can run in parallel. **Ownership is by directory, so the tracks never edit the same files.**

| Track | Owns | Never edits |
|:--|:--|:--|
| **Frontend (FE)** | `app/`, `components/`, `design/`, `lib/` (client code), `assets/`, client dependencies in `package.json`, `DESIGN.v2.md` (token additions only, with a handoff note) | `convex/` |
| **Backend (BE)** | `convex/` (read `convex/_generated/ai/guidelines.md` first), `tests/` for backend logic | `app/`, `components/`, `design/` |

- **Contracts first.** Section 6 defines every new or changed backend function. BE implements them exactly. FE codes against them and may stub them behind a small hook until BE lands (no fake data in shipped code paths).
- **Contract changes** need a handoff-log entry and Farzin's OK (AGENTS.md 20/80 rule 7).
- **Both tracks follow `AGENTS.md`.** No orphan code, indexed queries only, no speculative fields, validator/runtime parity, and never read env files.
- **Per-task done means:** the acceptance criteria are met, `npm run typecheck` passes, `npm test` passes, Convex codegen passes for BE tasks, the change was verified in the running app (web at `https://reed.localhost` via `make dev`, plus Android for gesture and keyboard work), and the checkbox is ticked with a one-line note.
